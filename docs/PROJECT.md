## 1. 项目目标与非目标

### 1.1 目标

1. **自动化重复操作**：把「界面 → 点击 → 等待 → 判断 → 再点击」这类固定循环交给程序。
2. **可维护**：游戏版本更新后，改动集中在「模板图」和「页面定义」，业务流程代码不动。
3. **可观测**：失败时自动留下现场截图与日志，不需要重跑一遍去复现。
4. **可验证**：不启动游戏也能用历史截图跑回归测试，快速定位是哪个识别点坏了。

### 1.2 非目标（当前阶段明确不做）

| 不做 | 原因 |
|---|---|
| 读内存、抓包、改协议 | 违反用户协议，封号风险最高 |
| 驱动级模拟输入 | 风险最高，且技术上难以维护 |
| 斗技、跨服等对抗场景 | 需要真人判断，脚本没有决策优势 |
| 追求极限速度 | 越快越像机器；正确性优先 |
| 通用游戏自动化框架 | 只服务阴阳师，不做过早抽象 |
| 实例间协作 | 单进程模型下实例零通信，见 3.4 |

### 1.3 关键约束

- **载体顺序**：桌面版（Windows 原生客户端）为第一阶段；MuMu 模拟器为第二阶段。
- **点击方式**：优先后台点击；不可用时切换前台，架构不变。
- **窗口状态**：游戏窗口**不得最小化**（最小化后通常不渲染，截图会黑）。
- **分辨率**：16:9 优先，逻辑基准 1280×720，兼容等比缩放；桌面版实际画面比例待实测。
- **实例**：一个进程只控制一个窗口；多开 = 多个进程。
- **环境可固定**：窗口尺寸、系统缩放比例一旦定下不再改动。
- **庭院皮肤固定**：模板是在当前皮肤下采集的。换皮肤会让底部导航栏整体位移十几像素
  （背景框变了、内边距跟着变），而静态模板的阈值是 0.95，位移后得分掉到 0.90~0.93 就会失配。
  真要换皮肤，必须重新标注受影响的模板，或把阈值降到 0.90。
- **分辨率统一**：所有实例都拉到 1280×720（16:9）。模板是分辨率绑定的——
  1280×720 下采的模板，在 800×450 的画面上得分只有 0.25~0.53，全部失配。

## 2. 设计原则

冲突时以序号靠前的为准。

1. **单一识别入口**：所有图像识别只走一个模块。禁止在业务流程里直接调用图像库。
2. **声明式优先于命令式**：界面长什么样、按钮在哪，用数据描述，不用代码逐行写死。
3. **流程只表达业务语义**：流程里出现的是「进入御魂 → 点挑战 → 等结算」，不是坐标和像素。
4. **依赖单向**：`flows → pages → core`，反向依赖一律禁止。
5. **失败必留证据**：任何识别失败或超时，自动落盘截图 + 上下文，不许静默重试。
6. **离线可回归**：能用历史截图验证的逻辑，不依赖真机验证。
7. **一进程一设备**：进程内不存在"另一个实例"，因此不可能出现跨实例串数据。
8. **能力与意图分离**：`ctx` 提供"看得见、点得中"，业务判断留在 `flows`，双方都不越界。

## 3. 系统架构

### 3.1 分层

| 层 | 职责 | 是否随游戏更新变化 |
|---|---|---|
| **设备层** `core/device/` | 窗口绑定、截图、点击、滑动 | 几乎不变 |
| **识别层** `core/vision/` | 模板匹配、OCR、颜色判断 | 几乎不变 |
| **页面层** `game/pages/` | 一个界面一个定义：长什么样、有哪些元素 | **主要变化区** |
| **流程层** `game/flows/` | 业务编排：先做什么、失败怎么办 | 基本不变 |

### 3.2 依赖规则（硬约束）

```
flows  →  pages  →  core
```

- `core/` 不得 import `game/`（core 不知道阴阳师存在）。
- `pages/` 不得 import `flows/`。
- 同层尽量不互相 import；需要共用时下沉到 `core/`。

可执行判据：`core` 里一旦出现「御魂」「结界」这类词，说明抽象漏了。

### 3.3 一次点击的完整数据流

以「点击御魂界面的挑战按钮」为例：

1. 流程层：`ctx.tap(SoulPage.CHALLENGE)`
2. 会话层从页面定义取出该元素：模板 key、搜索区域、阈值
3. 向设备层要一帧：`device.screenshot()`
4. 识别层把帧缩放到 1280×720 逻辑画布
5. 识别层在 roi 内做模板匹配，得到逻辑坐标与置信度
6. 得分低于阈值 → 抛 `ElementNotFound` → 进入恢复
7. 达标 → 逻辑坐标按比例换算为窗口客户区坐标
8. 设备层把点击消息投递给窗口
9. 全链路写一条结构化日志（步骤、页面、得分、耗时、截图）

**关键点**：第 8 步在后台点击模式下**不报错也可能是无效的**，所以"点击成功"永远以第 2 次识别（页面变化）为准，不以函数返回为准。

### 3.4 部署形态（多开）

```
启动脚本 / 任务计划
   ├─ 进程 1  --instance A  → 窗口 A  （独立 ctx、独立日志、独立失败域）
   ├─ 进程 2  --instance B  → 窗口 B
   └─ 进程 3  --instance C  → 窗口 C
```

- 每个进程：一个设备 → 一个 `ctx` → 一次流程执行。
- 进程之间**零通信**，互不影响；崩溃、卡死、重启都只作用于单个实例。
- 并发还是串行由启动脚本决定，核心代码不感知。
- **代价**：每个进程各自加载 OpenCV / OCR 模型，内存随实例数线性增长（见 12 节）。
- **限制**：做不了「两个账号互相配合」的玩法。

## 5. 模块设计

### 5.1 设备层 `core/device/`

**职责**：窗口绑定、截图、点击。不懂游戏，不做识别。

| 接口 | 输入 | 输出 | 说明 |
|---|---|---|---|
| `screenshot()` | — | 图像帧 + 客户区尺寸 | 返回客户区画面；失败时抛异常，**不得返回黑图** |
| `tap(x, y)` | 客户区坐标 | — | 按 `click_mode` 投递点击 |
| `swipe(...)` | 起止坐标、时长 | — | 滚动列表用 |
| `back()` | — | — | 发送返回键 / 点击返回按钮 |
| `client_size()` | — | 宽、高 | 客户区尺寸，用于坐标换算 |

#### 5.1.1 窗口绑定流程

1. 枚举所有顶层窗口，过滤：无标题、不可见、面积过小。
2. 打印列表：`序号 | 窗口标题 | 进程名 | 客户区尺寸`。
3. 用户选择序号。
4. 保存到 `configs/instances/<实例名>.yaml`：`title_match`（包含匹配）+ `match_index`（第几个匹配）。
5. 下次启动按此规则查找；找不到则报错退出，不自动猜。

**为什么不用句柄或 PID**：两者每次启动都会变。标题相对稳定，但可能带版本号或账号名，所以用**包含匹配**；多开时标题可能完全相同，靠 `match_index` 区分。

**绑定校验**：绑定成功后必须打印客户区尺寸并校验宽高比。绑错窗口时这一条能立刻暴露（尺寸或比例不符）。

#### 5.1.2 点击策略

| 模式 | 做法 | 优点 | 风险 |
|---|---|---|---|
| `background`（默认） | 向窗口投递鼠标消息（移动→按下→抬起），坐标为客户区坐标 | 不抢鼠标、可多窗口并行 | **可能被游戏忽略** |
| `foreground`（退路） | 激活窗口后用系统级输入模拟点击 | 兼容性最好 | 抢焦点，多开需串行 |

- 模式写在 `device.yaml`，切换不改任何上层代码。
- 后台点击无效时**不报错**，因此必须有回读验证（见 3.3 与 9 节）。
- 硬约束：窗口不可最小化。

#### 5.1.3 载体实现

- `desktop`：Windows 窗口句柄 + 客户区截图 + 消息投递。第一阶段实现。
- `mumu`：adb 截图与点击。第二阶段，用于对比与兜底。
- `mock`：回放录好的帧序列，供离线测试。

### 5.2 识别层 `core/vision/`

**职责**：给定一帧和一个查询，返回位置、文本或置信度。**不自己截图**（帧由调用方传入，这是离线测试成立的前提）。

| 通道 | 用途 | 相对成本 | 稳定性 |
|---|---|---|---|
| 颜色/区域快检 | 预筛"大概在哪个界面" | 极低 | 低 |
| 模板匹配 | 找按钮、图标 | 中 | 中，最常用 |
| OCR | 读体力、次数、勾玉等数值 | 高 | 高（语义明确） |

#### 5.2.1 OCR 设计要点

- **只读需要的区域**：声明 roi，不做全屏 OCR。
- **预处理**：放大、灰度、二值化。数字识别对预处理敏感，需要逐项标定。
- **缓存**：同一帧不重复 OCR（一次 OCR 可能比模板匹配慢一个数量级）。
- **精度验证**：同一画面连续读 20 次，记录一致率；不一致就要调预处理，不要靠"平均一下"掩盖。
- **失败语义**：读不出来必须返回"未知"并留证据，**不得返回 0**——0 会被业务逻辑当成"体力耗尽"，是典型的静默错误。
- **按需加载**：模型在第一次 OCR 时才载入，减少多开时的常驻内存。

### 5.3 页面层 `game/pages/`

**职责**：描述「这个界面长什么样」。这是游戏更新时唯一需要频繁改的地方。

**粒度约定：一屏一个页面定义。** 弹窗、结算面板、加载层都算独立页面，因为它们的锚点唯一且必须优先处理。

| 字段 | 含义 |
|---|---|
| `key` | 页面标识 |
| `anchors` | 1~3 个锚点模板，全部命中才算在这个页面；锚点必须是本页独有的 |
| `elements` | `El`（图像）或 `Text`（文字/数字） |
| `priority` | 多页面同时命中时的优先级；弹窗类设高 |

**元素声明**

| 类型 | 声明内容 | 通过什么识别 |
|---|---|---|
| `El` | 模板 key、roi、阈值、是否可选 | 模板匹配 |
| `Text` | 模板/区域、roi、类型（数字或文本） | OCR |

**页面判定规则**

1. 对每个已注册页面检查锚点是否全部命中。
2. 命中集合取优先级最高者。
3. 一个都不命中 → 判为「未知页面」，触发恢复，**不许猜**。

**锚点冲突自检**：提供工具把所有页面的锚点两两比对，输出「可能同时命中」的组合。一屏一个粒度下页面数量多，这个自检能省掉大量莫名误判。

### 5.4 会话层 `core/session/`（`ctx`）

**职责**：把「设备 + 识别 + 页面」组合成流程能直接用的动作，并统一处理超时、日志、恢复。

| API | 语义 |
|---|---|
| `shot()` | 抓一帧当前画面 |
| `detect()` | 当前是哪个页面；认不出返回 None |
| `require(page)` | 确认就在这个页面，不在就抛 WrongPage |
| `expect(page, timeout)` | 等到出现某页面；超时抛异常并说明当前页面 |
| `wait_any(*pages, timeout)` | 等任意一个出现，返回命中的页面 |
| `locate(element)` | 找到元素，返回中心坐标和得分；不点击 |
| `tap(element)` | 找到元素并点击（位置与按压时长都是随机的）|

刻意**不提供**的组合：`goto` / `back` / `seen` / `text` —— 能由上面这些拼出来的就不单独写。
需要「点哪个」就用 `tap`，需要「等到哪」就用 `expect` / `wait_any`。

**关键设计**

- **注入而非全局**：`ctx` 的依赖（设备、识别、路由、日志、恢复、配置）由 `main.py` 构造后传入，`ctx` 自己不 new。
  - 可测试：传 mock 设备即可离线跑流程
  - 可换载体：换设备实现只改装配处
  - 依赖显式：看签名就知道流程依赖什么
- **能力与意图分离**：`ctx` 只管「看得见、点得中、等得到」，**不存业务状态**（已刷次数、进度等属于 `flows`）。业务状态一旦进 `ctx`，它会膨胀成上帝对象。
- `ctx` 是流程层能看到的**唯一**接口，流程不得直接触碰 vision / device。

### 5.5 流程层 `game/flows/`

**职责**：业务编排。一个流程 = 一个可独立运行的任务。

- 只调用 `ctx`，不出现坐标、模板名、图像 API。
- 可参数化：次数、停止条件。
- **可中断、可续跑**：进度写状态文件，中断后能接着来（无人值守的前提）。
- 返回结构化结果（成功 / 部分成功 / 失败原因），不靠异常穿透顶层。
- 处理 OCR 数值：`ctx.text()` 拿到数字后做业务判断；拿到"未知"时按保守策略处理（暂停并告警，而不是当成 0）。

### 5.6 恢复 `core/recovery/`

| 异常 | 触发条件 | 恢复动作（代价从低到高） |
|---|---|---|
| `ElementNotFound` | 模板未达阈值 | 等待重试 → 关弹窗 → 回主界面 |
| `PageNotFound` | 锚点全不命中 | 关弹窗 → 返回上级 → 回主界面 |
| `Timeout` | 条件等待超时 | 同上，并提升截图留存等级 |
| `UnexpectedPopup` | 识别到活动/公告弹窗 | 点关闭 → 通用关闭位兜底 |
| `ClickIneffective` | 点击后画面无变化 | 重试点击 → 切前台模式 → 告警 |
| `OcrUnknown` | 数值读不出 | 重读 → 放大区域重试 → 告警 |
| `DeviceError` | 截图黑图/窗口消失 | 重新绑定窗口 → 告警退出 |

- 恢复有预算：同一任务连续恢复超过 N 次即停下告警，避免无限循环。
- 是否能自动重启游戏/模拟器 **待定**（第 14 节 ②），这决定恢复链的上限。
- `ClickIneffective` 是后台点击模式特有的：**点击必须靠画面变化验证**。

## 6. 分辨率适配

**核心思路**：不让程序"适配多分辨率"，而是让它**永远只见到一个尺寸**。

1. 设备层返回客户区画面。
2. 识别层统一缩放到 **1280×720** 逻辑画布。
3. 所有识别与元素坐标都在逻辑画布上计算。
4. 点击时把逻辑坐标按比例换算回客户区坐标。

**硬性要求**

| 项 | 要求 |
|---|---|
| 缩放算法 | 缩小 `INTER_AREA`，放大 `INTER_LINEAR`；禁止最近邻 |
| 宽高比校验 | 归一化前检查，偏离目标比例超 1% 直接报错，不静默变形 |
| 黑边处理 | 截客户区；检测到黑边先裁有效区域再缩放 |
| 阈值标定 | 按实际分辨率实测最低得分，阈值取其下浮 5~10%，不写全局固定值 |
| 模板来源 | 只在基准分辨率下采集一套 |

**桌面版特有步骤（P0 必须先做）**

1. 截一张客户区画面，测量实际像素尺寸。
2. 计算宽高比，确认是否为 16:9；若不是，重新确定逻辑基准。
3. 检查系统缩放（125%/150%）是否影响截图尺寸；必要时让程序声明 DPI 感知。

**验证方法**：不同分辨率截同一界面 → 都缩放到逻辑画布 → 相减看差异。差异集中在背景/特效则纯缩放成立；元素整体位移则需引入锚点相对布局。

## 7. 数据与配置

### 7.1 模板清单 `assets/pages/<页面>/templates.yaml`

每个界面一个文件夹，模板图和它的清单放在一起：

```
assets/pages/home/
├─ templates.yaml
├─ explore.png
└─ guild_entry.png
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `file` | 是 | 相对所在页面文件夹的路径（通常就是 `<元素名>.png`）|
| `roi` | 是 | 归一化搜索区域，限定范围提速并降低误匹配 |
| `threshold` | 是 | 实测得分下浮后的值 |
| `since` | 否 | 最后验证通过的日期/游戏版本 |
| `note` | 否 | 对应什么按钮 |

页面里有哪些元素、哪些是锚点，写在代码里（`game/pages/<页面>.py`）；
清单只放会随游戏更新变化的参数。两者是否对得上由 `python -m tools.check_pages` 检查。

页面名与元素名只允许字母、数字、下划线、横线——它们直接变成文件夹名和文件名。

### 7.2 实例配置 `configs/instances/<实例名>.yaml`

一个实例一个文件，文件名就是实例名。

| 字段 | 说明 |
|---|---|
| `title_match` | 窗口标题的包含匹配串（通常就是角色名）|
| `match_index` | 同名窗口里的第几个（多开时区分）|
| `client` | 绑定时记录的客户区尺寸，仅供显示，可能已过时 |

启动时用 `--instance <name>` 选择；只有一个配置时可省略。

### 7.3 设备参数

目前没有独立的设备配置文件，参数都是 `core/device/desktop.py` 里的常量：

| 常量 | 当前值 | 含义 |
|---|---|---|
| `TARGET_ASPECT` | 16/9 | 客户区应有的宽高比 |
| `ASPECT_TOLERANCE` | 0.0 | 偏差容忍度；0 表示不是精确 16:9 就调整 |
| `TARGET_CLIENT_SIZE` | 1280×720 | 比例不对时强制改成的尺寸，与模板采集分辨率一致 |
| `TITLE_SEPARATOR` | `" · "` | 窗口标题里「角色 · 服务器」的分隔符 |
| `GAME_PROCESS` | `onmyoji` | 判定游戏窗口用的进程名（不含扩展名）|

### 7.4 任务配置

尚未实现。任务列表、次数、停止条件将来放 `configs/tasks.yaml`。

**形式**：JSONL，每行一条，便于 grep 与分析。

**每条至少包含**：时间、实例名、任务、步骤、当前页面、动作、目标、置信度、耗时。

## 9. 测试策略

| 层级 | 方式 | 验证什么 |
|---|---|---|
| 单元测试 | 纯函数（`core/vision`、`core/humanize`）| 坐标换算、阈值比较、随机分布 |
| 回归测试 | 历史截图 + `tools/whereami --file` | 每张截图应被识别为预期页面 |
| 流程测试 | 假设备回放帧 | 完整流程的动作序列是否正确 |
| 设备测试 | `tools/doctor.py` | 解释器/依赖/路径/管理员权限是否就绪 |

**回归测试是维护性的核心**：`tests/screens/<分辨率>/` 存各分辨率截图，游戏更新后跑一次即可定位失效模板。
（`tests/` 目录尚未创建，目前靠 `tools/whereami --file` 手工验证历史截图。）

**约定**：改动涉及识别 / 页面 / 流程，必须跑回归并给出结果；不接受「真机跑一遍没报错」作为验证依据。

**后台点击必须回读**：任何点击类操作都要有后续的 `expect` 或 `seen` 验证画面变化，这是 `ClickIneffective` 异常的唯一来源。

## 10. 版本适配 SOP（游戏更新后）

1. 任务报错 → 看运行器窗口里的「原因 + 建议」，或去 `artifacts/` 找失败截图。
2. 跑 `python -m tools.check_pages`：引用的模板是否还存在、图片是否缺失、有没有纯色模板。
3. 跑 `python -m tools.whereami --instance <名字>`：哪些模板得分掉了。
4. 用 `tools/workbench.py` 修：选中模板看匹配位置，或重新框选保存；必要时更新 `since`。
5. 布局整体变化 → 改对应 `game/pages/*.py`。
6. 流程变化（新增确认弹窗、步骤增减）→ 改 `game/flows/*.py`。
7. `CHANGELOG.md` 记一条：改了哪个界面、哪张图、为什么。
8. 重跑检查 + 真机验证。

**判据**：一次更新需要改 `flows/`，说明是玩法变化而非普通 UI 更新，要额外补回归样本。

## 11. 开发路线

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| **P0 可行性实验** | 枚举窗口 → 截图 → 后台点击 → 回读 | 半小时内得出「桌面版是否可行、点击用哪种模式」 |
| **P1 工具** | `list_windows` / `pick_window` / `capture` / `workbench` / `whereami` / `check_pages` / `doctor` | 能在工作台里截图、框选生成模板、核对 roi；能给任意截图报告命中情况 |
| **P2 识别骨架** | 设备层 + 识别层 + 页面注册表 + 回归测试 | 正确识别 3 个以上界面；回归可跑 |
| **P3 单任务闭环** | 会话层 + 流程 + 运行器 + 恢复 | 一个任务无人值守连跑 20 次不卡死 |
| **P4 OCR** | 数值读取 + 精度验证 | 体力/次数读取 20 次一致率达标 |
| **P5 多开** | 一实例一配置 + 启动脚本 + 窗口绑定验证 | 两个实例并行互不干扰，日志分开 |
| **P6 MuMu 适配** | adb 设备后端 | 同一套页面/流程在模拟器上通过回归 |

**顺序约束**

- P0 是一道闸门：结论是「不可行」时，先回到载体选型再谈后续。
- P2 阶段就把 `Text` 元素类型定义好（接口层面），OCR 实现留到 P4——避免风格返工，也避免过早引入复杂度。
- P4 之前不要加第二个任务。第二个任务的价值远低于「第一个任务能被验证」。
- P5 多开放在单实例稳定之后：多开只是把单实例跑两遍，架构风险最低。

## 12. 风险与约束

| 风险 | 影响 | 应对 |
|---|---|---|
| 后台点击被游戏忽略 | 点了没反应且不报错 | P0 先验证；保留前台模式开关；所有点击靠画面回读验证 |
| GPU 渲染导致截图黑屏 | 完全无法识别 | P0 判定；换截图方式；不可行则回 MuMu |
| 窗口最小化后不渲染 | 截图黑 | 文档写明硬约束；启动时检测窗口是否最小化并告警 |
| 系统 DPI 缩放 | 截图尺寸与预期不符、点击偏移 | 程序声明 DPI 感知；绑定后校验客户区尺寸 |
| 多开标题重复 | 绑错窗口，两个实例抢一个 | 标题包含匹配 + `match_index`；启动打印绑定信息；校验尺寸 |
| 多开时焦点争抢 | 前台模式下点击互相打断 | 后台模式优先；退化为前台时由启动脚本串行 |
| OCR 模型内存 × N | 多开时内存线性上涨 | 模型按需加载；实测单实例内存占用后再定并发数 |
| OCR 读错数值 | 业务判断错误（如把体力当 0） | 读不出返回"未知"而非 0；20 次一致率验证 |
| 官方禁止第三方辅助 | 封号 | 控制频率、人类化延迟、敏感场景不用、接受风险 |
| UI 大改版 | 大量模板失效 | 回归测试快速定位；页面/流程分层把改动限制在局部 |

## 13. 术语表

| 术语 | 含义 |
|---|---|
| 逻辑画布 / 逻辑分辨率 | 所有识别统一缩放到的固定尺寸，本项目为 1280×720 |
| 客户区 | 窗口去掉标题栏与边框后的画面区域，截图的正确对象 |
| 锚点 anchor | 用于判定"是不是这个页面"的特征模板 |
| ROI | 搜索区域，限定匹配范围，归一化坐标表示 |
| 阈值 threshold | 模板匹配得分下限 |
| 后台点击 | 直接向窗口投递鼠标消息，不移动真实光标、不切换前台 |
| 回读验证 | 操作后重新识别画面，用画面变化确认操作生效 |
| 恢复 recovery | 失败后把游戏拉回可控状态的动作序列 |
| 实例 instance | 一个游戏窗口 + 一个进程 + 一份配置 |
| 回归测试 | 用历史截图验证识别逻辑仍然成立的测试 |
